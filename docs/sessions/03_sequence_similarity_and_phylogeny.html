3.2 Theory (≈45 min)

3.2.1 1. Similarity search: what BLAST actually measures

grep (Sessions 1-2) finds exact text. Biological sequences almost never match exactly: mutation, sequencing error, and evolutionary divergence all change a handful of bases here and there. BLAST (Basic Local Alignment Search Tool) finds sequences that are similar enough, scores how similar, and does it against thousands of sequences at once, in seconds.

Given one query sequence and a set of reference sequences, blastn reports one row per match it considers meaningful:

Column Meaning
pident percent identity: of the aligned bases, what fraction are identical
length how many bases the alignment covers
evalue how many matches this good would be expected by chance alone; smaller is better, 0.0 means effectively impossible by chance
bitscore an overall match quality score, normalized so it is comparable between searches; higher is better

A high pident over a short length can still be a coincidence; a lower pident over a long length with a tiny evalue usually is not. Reading a BLAST hit means looking at these together, not just the percent identity on its own. Block B gives you a real case where trusting pident alone would mislead you.

TipWhere you have already seen this idea

Session 1’s mystery.fasta contained one record, sp|P0DTC2|SPIKE_SARS2, that was neither obviously DNA nor identifiable by eye. A similarity search is exactly the next step you would take on a record like that: not “does it look like DNA”, but “what does it match”. You meet that exact sequence again at the end of this theory block.

Search settings matter, too. BLAST can run in a fast, strict mode tuned for near-identical sequences, or a slower, more sensitive mode that also reports weaker, more distant matches. Neither is “wrong”; they answer slightly different questions, and today’s practical uses both, deliberately, one after the other.

3.2.2 2. From one match to a tree

BLAST answers “what is my sequence most similar to”, one hit at a time. A phylogenetic tree goes further: it places every sequence you give it, including ones too different from each other for a strict BLAST search to confidently match, on a single diagram of relative relatedness. Three steps get you there:

  1. Multiple sequence alignment. Every sequence is stacked and padded with gaps (-) so that the same column means the same position in every sequence. Session 2’s FASTQ lines were already the same length by construction; here, alignment is the step that creates that correspondence across sequences that differ in length.
  2. Distance. Once sequences line up column by column, counting the fraction of columns that differ between every pair of sequences gives a distance: more differences, more distant. Doing this for every pair at once gives a distance matrix, one number per pair; today you will read it as a table, the same idea scales to a colour-coded heatmap for larger datasets than today’s.
  3. Tree building. An algorithm arranges sequences on a tree so that closely related sequences sit together, joined by a recent common node. Today’s tool, FastTree, does this quickly even for larger alignments than ours, using a statistical (approximately maximum-likelihood) model rather than the distance matrix alone, and it reports a support value at each split: roughly, how confident the method is that this grouping is real rather than an artefact of this particular alignment.
TipReading a tree
Term Meaning
Tip one sequence, labelled, at the end of a branch
Node a point where branches split: the inferred common ancestor of everything beyond it
Branch length genetic distance (not necessarily time) between a node and the sequence or node it leads to
Clade a node plus everything descended from it: a complete sub-group
Outgroup a sequence known to be the most distantly related, used to anchor which end of the tree is the root
Support value confidence (here, 0 to 1) that a given split is real, from resampling the alignment many times and checking how often the same split reappears

Two tips drawn close together are closely related because of where their shared node is, not because they happen to be printed near each other. Always trace back to the node.

FastTree’s speed comes from heuristics, not from skipping statistics: it is a fast, reasonable first answer, not the last word on a dataset this size. One known weakness, relevant for today’s most distant sequences: raw percent-difference, the simplest possible distance, underestimates true evolutionary distance once enough time has passed for the same site to mutate more than once (“saturation”). Distance correction models (for example Jukes-Cantor) attempt to account for this. A full, maximum-likelihood tree with properly resampled bootstrap support (rather than FastTree’s faster approximation) is the published standard, and out of scope for today, but the optional challenge lets you try a correction model on today’s data.

3.2.3 3. Worked example: a family of coronaviruses

Coronaviruses that infect humans are not one thing: SARS-CoV-2, SARS-CoV-1 (the 2003 SARS outbreak), MERS-CoV, and several seasonal “common cold” coronaviruses are all related, but to very different degrees. Some share a recent common ancestor; others split off much earlier. Comparing one gene, the spike gene (S), the gene for the protein coronaviruses use to enter a host cell, across several of these viruses is a standard way virologists work out exactly that: which ones are close relatives, and which are more like distant cousins. That is precisely today’s practical, on real sequences from these real viruses, checked at both the nucleotide and the protein level.

TipTwo-minute detour: the same logic on a protein, via UniProt

Session 1’s unidentified record, sp|P0DTC2|SPIKE_SARS2, is the SARS-CoV-2 spike protein. P0DTC2 is its accession in UniProt, a curated protein database: look it up and, instead of raw sequence, you get functional annotation: named domains (receptor-binding domain, furin cleavage site, signal peptide, transmembrane region), and links to solved 3D structures. A protein search (blastp) works exactly like blastn, just on amino acids instead of bases; block D2 has you run it on this exact protein.

TipOptional, for students who are ahead

## Theory (≈45 min)

### 1. Similarity search: what BLAST actually measures

`grep` (Sessions 1-2) finds **exact** text. Biological sequences almost never match
exactly: mutation, sequencing error, and evolutionary divergence all change a handful of
bases here and there. **BLAST** (Basic Local Alignment Search Tool) finds sequences that
are *similar enough*, scores how similar, and does it against thousands of sequences at
once, in seconds.

Given one query sequence and a set of reference sequences, `blastn` reports one row per
match it considers meaningful:

| Column | Meaning |
|---|---|
| `pident` | percent identity: of the aligned bases, what fraction are identical |
| `length` | how many bases the alignment covers |
| `evalue` | how many matches this good would be expected **by chance alone**; smaller is better, `0.0` means effectively impossible by chance |
| `bitscore` | an overall match quality score, normalized so it is comparable between searches; higher is better |

A high `pident` over a short `length` can still be a coincidence; a lower `pident` over a
long `length` with a tiny `evalue` usually is not. Reading a BLAST hit means looking at
these together, not just the percent identity on its own. Block B gives you a real case
where trusting `pident` alone would mislead you.

::: callout-tip
## Where you have already seen this idea

Session 1's `mystery.fasta` contained one record, `sp|P0DTC2|SPIKE_SARS2`, that was
neither obviously DNA nor identifiable by eye. A similarity search is exactly the next
step you would take on a record like that: not "does it look like DNA", but "what does it
match". You meet that exact sequence again at the end of this theory block.
:::

Search settings matter, too. BLAST can run in a fast, strict mode tuned for near-identical
sequences, or a slower, more sensitive mode that also reports weaker, more distant
matches. Neither is "wrong"; they answer slightly different questions, and today's
practical uses both, deliberately, one after the other.

### 2. From one match to a tree

BLAST answers "what is my sequence most similar to", one hit at a time. A **phylogenetic
tree** goes further: it places every sequence you give it, including ones too different
from each other for a strict BLAST search to confidently match, on a single diagram of
relative relatedness. Three steps get you there:

1. **Multiple sequence alignment.** Every sequence is stacked and padded with gaps (`-`)
   so that the same column means the same position in every sequence. Session 2's FASTQ
   lines were already the same length by construction; here, alignment is the step that
   *creates* that correspondence across sequences that differ in length.
2. **Distance.** Once sequences line up column by column, counting the fraction of
   columns that differ between every pair of sequences gives a distance: more differences,
   more distant. Doing this for every pair at once gives a **distance matrix**, one number
   per pair; today you will read it as a table, the same idea scales to a colour-coded
   **heatmap** for larger datasets than today's.
3. **Tree building.** An algorithm arranges sequences on a tree so that closely related
   sequences sit together, joined by a recent common node. Today's tool, **FastTree**,
   does this quickly even for larger alignments than ours, using a statistical
   (approximately maximum-likelihood) model rather than the distance matrix alone, and it
   reports a **support value** at each split: roughly, how confident the method is that
   this grouping is real rather than an artefact of this particular alignment.

::: callout-tip
## Reading a tree

| Term | Meaning |
|---|---|
| **Tip** | one sequence, labelled, at the end of a branch |
| **Node** | a point where branches split: the inferred common ancestor of everything beyond it |
| **Branch length** | genetic distance (not necessarily time) between a node and the sequence or node it leads to |
| **Clade** | a node plus everything descended from it: a complete sub-group |
| **Outgroup** | a sequence known to be the most distantly related, used to anchor which end of the tree is the root |
| **Support value** | confidence (here, 0 to 1) that a given split is real, from resampling the alignment many times and checking how often the same split reappears |

Two tips drawn close together are closely related **because of where their shared node
is**, not because they happen to be printed near each other. Always trace back to the
node.
:::

FastTree's speed comes from heuristics, not from skipping statistics: it is a fast,
reasonable first answer, not the last word on a dataset this size. One known weakness,
relevant for today's most distant sequences: raw percent-difference, the simplest possible
distance, *underestimates* true evolutionary distance once enough time has passed for the
same site to mutate more than once ("saturation"). Distance **correction models** (for
example Jukes-Cantor) attempt to account for this. A full, maximum-likelihood tree with
properly resampled bootstrap support (rather than FastTree's faster approximation) is the
published standard, and out of scope for today, but the optional challenge lets you try a
correction model on today's data.

### 3. Worked example: a family of coronaviruses

Coronaviruses that infect humans are not one thing: **SARS-CoV-2**, **SARS-CoV-1** (the
2003 SARS outbreak), **MERS-CoV**, and several seasonal "common cold" coronaviruses are
all related, but to very different degrees. Some share a recent common ancestor; others
split off much earlier. Comparing one gene, the **spike gene** (`S`), the gene for the
protein coronaviruses use to enter a host cell, across several of these viruses is a
standard way virologists work out exactly that: which ones are close relatives, and which
are more like distant cousins. That is precisely today's practical, on real sequences
from these real viruses, checked at both the nucleotide and the protein level.

## Bonus: a rigorous tree, for real (IQ-TREE) {.unnumbered}

::: callout-tip
## Optional, for students who are ahead

**This is not part of the course.** No marks depend on it, and no later session assumes
you have done it. It exists because the theory block named two things FastTree
approximates for speed, a proper substitution model and real bootstrap support, and
leaves them "out of scope." This bonus is that scope, on the exact same alignment you
already have.
:::

FastTree assumed a simple substitution model (Jukes-Cantor: every base equally likely to
mutate into every other) and estimates support with a fast approximation (SH-like,
roughly "how often does this split survive small random tweaks"). **IQ-TREE** does both
properly, at real computational cost: **ModelFinder** tests dozens of substitution models
(different rules for how often each base swaps for each other one, whether some sites
mutate faster than others) and picks the one that fits your data best by a statistical
criterion, then **ultrafast bootstrap** rebuilds the tree 1,000 times, each time from a
random resample of the alignment's columns, and reports what fraction of those 1,000
trees agree with each split in the final one. That is what a bootstrap support value
(typically written as a percentage, out of 100) actually counts.

### Try it (1-2 minutes to run)

```bash
module load IQ-TREE
iqtree3 -s aligned_spike.fasta -m MFP -B 1000 -T AUTO --prefix ../results/iqtree_bonus
```

`-m MFP` runs ModelFinder before building anything. `-B 1000` requests 1,000 ultrafast
bootstrap replicates. `-T AUTO` lets IQ-TREE pick how many threads to use.

::: callout-note
## Checkpoint

This takes noticeably longer than FastTree, roughly a minute or two on LEGcompute, not
under a second: proper model selection and 1,000 real resamples cost real time. When it
finishes, `../results/iqtree_bonus.iqtree` is a full text report; the one line to find is
"Best-fit model according to BIC". `../results/iqtree_bonus.treefile` is the tree itself,
in Newick format exactly like FastTree's output, except each internal split is now
labelled with a number out of 100 rather than FastTree's 0-1 scale.
:::

Open `plot_tree.R`, duplicate the line that reads the tree, and point the copy at
`"../results/iqtree_bonus.treefile"` instead, to plot this one the same way. Two questions
worth answering for yourself, not submitted anywhere:

- Is the **topology** (which sequences group together) the same as your FastTree tree?
- Are the **bootstrap values** close to FastTree's support values, or different? Given
  that one is a fast approximation and the other resamples the data 1,000 times, what
  would you expect, and why might a real difference (if you see one) matter more on a
  harder dataset than on this one?

### Go further

Open `../results/iqtree_bonus.iqtree` in a text editor and find the "SUBSTITUTION PROCESS"
section near the end, where "Rate parameter R" and "State frequencies" sit a few lines
below the model name. These are the actual numbers ModelFinder fit to your data: for
example, how much more often a transition (A<->G or C<->T) happens than a transversion,
for these five coronavirus spike genes specifically, rather than assumed equal as
FastTree's default model assumes.
